# Задание 1. Анализ и планирование

«Тёплый дом» — это небольшая компания, которая организует удалённое управление отоплением в доме. В настоящий момент компания обслуживает 100 пользователей.
Недавно она выиграла тендер и получила заказ на создание экосистемы умных посёлков на территории нескольких регионов страны.
Чтобы выполнить заказ, компании необходимо расширить функционал своей системы и масштабировать её. Экосистема должна позволить пользователям управлять не только  отоплением, но и умными устройствами в доме. Чтобы подключить дом к экосистеме, пользователям необходимо установить специальные датчики и реле. Сейчас они есть только в половине домов, которые хотят подключиться.

### 1. Описание функциональности монолитного приложения
В настоящий момент приложение содержит следующую функциональность:
**Управление отоплением:**

- Пользователи могут включать и выключать отопление в доме, а также получать текущее состояние системы отопления, включая текущую и целевую температуру.
- Система поддерживает только управление отоплением. 
- Для установки и обновления системы необходим выезд инженера.

**Мониторинг температуры:**

- Пользователи могут получить текущее значение температуры в доме.
- Система поддерживает только температурные датчики, установленные специалистами компании.

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Java
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно через REST API.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развёртывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Описание доменов и границ контекстов дано для целевой системы.
1. Управление устройствами. Управление состоянием устройств в умном доме (включение/выключение, настройка параметров). Примером такого устройства может служить устройство отопления в текущей системе.
2. Мониторинг устройств. Отображение состояния и параметров устройств как в реальном времени, так и в выбранный момент в прошлом, а также обработка и отображение "исторические даннные" в виде графиков и/или диаграмм. В текущей системы пользователь может мониторить только температуру. 
3. Конфигурирование устройств. "Оркестратор" устройств в умном доме, позволяющий программировать систему для управления различными модулями в соответствии со своими потребностями.
4. Управление уведомлениями. Обработка и отправка уведомлений пользователя о статусе системы в любом виде (push, email, sms).
5. Авторизация и аутентификация. Отвечает за авторизацию, аутентификацию и управление ролями


### **4. Проблемы монолитного решения**
В текущей ситуации (управление всего одной системой, 100 пользователей, небольшая команда) монолитная архитектура не вызывает проблем, разве что синхронные запросы желательно бы заменить на асинхронные. 
Однако, с учётом планов на значительное увеличение масштаба и расширение функционала уже в ближайшем будущем, существующее решение будет испытывать типичные проблемы монолитных решений: 
- Высокий риск ошибок. Изменения в одной части приложения могут непредсказуемо влиять на другие части.
- Длительные циклы разработки и развёртывания. При каждом изменении придётся тестировать всё приложение целиком.
- Трудности управления командой, особеннено с учётом скорого расширения команды разработчиков. Изменения, которые вносит одна команда, могут повлиять на работу других команд.
- Трудности масштабирования. Систему можно масштабировать только целиком (вертикальное масштабирование), а масштабирование отдельных компонентов системы сильно затруднено (практически невозможно).
